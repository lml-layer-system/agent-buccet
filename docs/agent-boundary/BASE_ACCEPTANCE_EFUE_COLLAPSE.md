# BASE ACCEPTANCE: EFUE COLLAPSE
**From Infinite Agent Capability Demand -> Finite Buccet Yes-Side Structure**

## PHASE 0: THE PROBLEM

The public expectation surface for agents looks infinite.

People want an agent that can:
- read and write documents
- search and debug code
- analyze spreadsheets and data
- research, summarize, and synthesize
- design visuals and artifacts
- manage tasks, notes, and memory
- run tests and workflows
- use apps, connectors, browsers, and APIs

If the Buccet yes side is too narrow, the agent feels dead.
If it is too loose, it becomes tool soup.

So the real problem is:

How do we make the Buccet yes side feel broad enough for almost all normal work right away, while keeping it bounded, clear, and lawful?

## PHASE 1: OPPOSING FORCES

### FORCE 1: YES-SIDE INFINITY (Y∞)

Y∞ = All the things people expect a real working agent to help them do.

Infinite-seeming demand surfaces:
- infinite apps
- infinite skills
- infinite workflows
- infinite domains
- infinite combinations of tools
- infinite task phrasing
- infinite output formats

Why it seems infinite:
- every catalog is huge
- every user has different work
- every workflow can branch and recombine

Size: INFINITE

### FORCE 2: YES-SIDE REQUIREMENTS (R)

R = What the Buccet yes side MUST satisfy to feel real and stay lawful.

For the base acceptance side, it MUST:

1. FEEL BROAD
   - should feel like normal work is already there on day 1
   - should not feel like a toy starter pack

2. STAY BOUNDED
   - no broad shell
   - no broad delete
   - no broad secrets access
   - no broad unsafe outbound motion

3. STAY READABLE
   - every entry should be clear
   - users should understand what it is and what it connects to

4. STAY CUSTOMIZABLE
   - easy to search, mute, remove, and diff
   - no hidden special-case systems

5. STAY COHERENT
   - yes side must feel like human work, not random tools
   - deny still overrides on overlap

6. STAY FACTORY-SHAPED
   - adding more should feel easy and repeatable
   - same UPL acceptance structure every time

Size: 6 core requirements

### FORCE 3: WHAT ACTUALLY WORKS (W)

W = Observable patterns of what makes agents feel broad and useful in practice.

What works:

1. DOCUMENT AND OFFICE WORK
   - docx, pptx, xlsx, coauthoring, docs editing

2. CODING AND DEBUGGING WORK
   - file search, debugging, tests, context shaping, project understanding

3. RESEARCH AND KNOWLEDGE WORK
   - search, synthesis, notebook flows, source-grounded retrieval

4. DATA AND REPORTING WORK
   - spreadsheets, analysis, dashboards, reporting, charts

5. DESIGN AND ARTIFACT WORK
   - frontend design, canvas design, themes, artifacts, diagrams

6. TASK AND MEMORY WORK
   - notes, reminders, calendars, planning, orchestration

7. APP AND CONNECTOR WORK
   - bounded integrations, connectors, MCP-style workflows, provider use

8. TESTING AND QUALITY WORK
   - webapp testing, test writing, test data, quality checks

9. BROWSER-BACKED NORMAL WORK
   - bounded browser use for ordinary workflow tasks, not stealth

These patterns are finite, reusable, and visible across the public skill ecosystems.

Size: 9 proven work surfaces

## PHASE 2: COLLISION POINT

Y∞ ⊓ R ⊓ W = BUCCET_BASE_ACCEPTANCE

What survives when:
- infinite agent capability demand
- meets bounded, readable Buccet requirements
- using the work surfaces that actually make agents feel useful

= A finite yes-side structure

The insight:

The Buccet yes side does not need infinite tool coverage.
It needs finite high-coverage dimensions that map to what normal people actually want done.

## PHASE 5: THE LAWS

### LAW 1: BROADNESS MUST FEEL HUMAN
**Invariant:** the yes side must map to real human work surfaces.
**Transformation:** new yes-side entries should improve practical day-1 usefulness.
**Enforcement:** acceptance inventories and workflow-shaped entries.
**Failure:** the pack feels technical but not useful.

### LAW 2: BOUNDING MUST REMAIN VISIBLE
**Invariant:** the yes side opens only bounded lawful motion.
**Transformation:** new entries stay in the same UPL acceptance structure.
**Enforcement:** action kinds, connects-to fields, bounds fields, and deny override.
**Failure:** acceptance becomes vague power instead of lawful roads.

### LAW 3: ADDITIONS MUST STAY FACTORY-SHAPED
**Invariant:** new sources should drop into the same acceptance factory cleanly.
**Transformation:** every source becomes ordinary UPL acceptance entries.
**Enforcement:** same renderer, same contract lane, same inventory structure.
**Failure:** the yes side becomes messy and hard to extend.

### LAW 4: BREADTH MUST BE DIMENSIONAL, NOT RANDOM
**Invariant:** growth should fill acceptance dimensions, not just add names.
**Transformation:** every new source should strengthen one or more of the 9 dimensions.
**Enforcement:** this EFUE map.
**Failure:** the pack grows without becoming more complete.

## THE FINAL ANSWER

The Buccet yes side is not about infinite tools.

It is about 9 finite dimensions of real work:
1. document / office
2. coding / debugging
3. research / knowledge
4. data / analytics
5. design / artifacts
6. tasks / memory
7. apps / connectors
8. testing / quality
9. bounded browser-backed work

That is the map.

From here, new sources should just widen those dimensions until the yes side feels undeniably top-tier.
